## tlb_bench — 大页对 TLB 的影响

对比同样大小的工作集，在 **4KB 普通页** 和 **2MB 大页** 上做随机访问的平均延迟。

### 为什么要用指针追逐

最直接的写法是这样，但它**测不出任何东西**：

```c
for (size_t i = 0; i < n; i++)
    sum += buf[i * STRIDE];          /* 顺序访问 */
```

两个原因，都是硬件在"帮忙"：

1. **硬件预取器识别出固定步长**，提前把数据和页表项都加载好
2. **访存可以并行**——地址互相独立，现代 CPU 能让十几个 cache miss 的延迟互相重叠

所以这里用的是**指针追逐**：

```c
p = *(void **)p;
```

把内存切成若干槽位，每个槽位开头存"下一个槽位的地址"，按**随机置换**串成环。下一次访问的地址**来自本次读到的值** → 存在真实数据依赖 → CPU 无法乱序、预取器无法预测、多次 miss 无法并行。

每次迭代的耗时，就是一次完整内存访问的延迟。

### 三个容易踩的坑

| 坑 | 后果 | 本代码怎么处理 |
|---|---|---|
| **置换退化** | 洗牌写错会变成轮转（恒定步长），预取器照样生效 | Fisher-Yates，`j` 的范围必须是 `[0, i]` |
| **透明大页污染对照组** | THP=always 时「4KB 组」也被提升成大页，两组都是大页 → 加速比≈1 | 注意：**见下方「已知限制」** |
| **死代码消除** | 循环结果没人用，`-O2` 下整个循环被删掉，测出 0 ns | `static volatile uintptr_t sink` 消费最终值 |

另外计时只在循环外各做一次（**成批测量**）——`clock_gettime` 自身开销约 12ns，和被测量的几十纳秒同量级，逐次计时会把结果彻底淹掉。

### 构建与运行

```bash
make
sudo ./tlb_bench [MB]        # 默认 256 MB
```

**需要 Linux**，且预留好大页：

```bash
# 256MB 工作集需要 128 个 2MB 大页
echo 256 | sudo tee /proc/sys/vm/nr_hugepages
grep HugePages_Free /proc/meminfo
```

> `MAP_HUGETLB` 是 Linux 专有的（2.6.32+）。**macOS 没有 hugetlbfs**，编译不过，这是预期行为。

### 结果怎么判断

| 现象 | 可能原因 |
|---|---|
| 加速比接近 1.0 | ① 工作集没超过 4KB 页的 TLB 覆盖（L2 STLB ~1536 项 × 4KB ≈ 6MB）② 预取器生效——检查置换是否真的随机 ③ **对照组被 THP 污染** |
| 延迟只有几纳秒 | 循环被编译器删了 |
| 大页分配失败 | `HugePages_Free` 不够 |
| 加速比超过 5 倍 | 可能叠加了 cache 效应，加大工作集或延长预热 |

## 实测结果（2026-09-13）

环境：阿里云 `ecs.c9i.large`，Intel Xeon 6982P-C @3.9GHz，Ubuntu 24.04 / 内核 6.8.0-138，
512×2MB 大页，**THP=madvise**（所以 4KB 对照组天然纯净）。

### 256MB 工作集，三次运行

| 次 | 4KB 页 | 2MB 大页 | 加速比 |
|---|---|---|---|
| 1 | 90.06 ns | 77.04 ns | 1.17x |
| 2 | 85.65 ns | 76.64 ns | 1.12x |
| 3 | 86.74 ns | 78.68 ns | 1.10x |

**加速比只有约 1.1x**——远低于「TLB 覆盖范围差 512 倍」暗示的量级。

### 但 perf 证明 TLB 完全按预期工作

```
                      4KB 页          2MB 大页        （128MB 工作集）
  平均延迟            47.12 ns        34.85 ns
  dTLB-load-misses    22,003,065      2,802
  miss 率             30.35%          0.01%
```

22M 次访问里 4KB 组 miss 了 2200 万次（几乎每次），大页组只 miss 2802 次。

### 结论：一次 TLB miss 只值约 12 纳秒

```
   47.12 - 34.85 = 12.27 ns ≈ 48 个周期 @3.9GHz
```

**不是「4 次内存访问 ≈ 320ns」。** 因为：

- 页表本身是**可缓存的普通内存**，顶层 PML4/PDPT 只有几张、被反复访问，几乎常驻 cache
- 现代 CPU 有 **page walk cache** 缓存中间级页表项，一次 walk 往往只需查最后一两级

### 工作集扫描

| 工作集 | 4KB | 2MB | 差值 | 加速比 |
|---|---|---|---|---|
| 64 MB | 42.98 | 33.51 | 9.47 | 1.28x |
| 128 MB | 47.64 | 34.81 | 12.83 | **1.33x** |
| 256 MB | 86.50 | 78.79 | 7.71 | 1.10x |
| 512 MB | 119.71 | 110.02 | 9.69 | 1.10x |
| 1024 MB | 137.01 | 116.91 | 20.10 | 1.18x |

**TLB 代价基本恒定在 8-13ns，而 base 延迟随工作集从 33ns 涨到 137ns**（cache line 总量 1MB→16MB，溢出 L3 落进 DRAM）。

```
   加速比 = (base + TLB代价) / base   →   base 越大，越接近 1
```

所以**工作集越大，大页的「加速比」反而越不显眼**，尽管 miss 的绝对次数更多。
1GB 那行差值反弹到 20ns 是二阶效应：页表本身涨到 2MB，page walk 自己也开始 miss 了。

### 注意：适用边界

- **虚拟机环境**，guest 里是 EPT 二维页表，TLB miss 最坏代价比物理机大，**绝对值不能外推到物理机**
- 单物理核，无多核/NUMA 干扰
- `dtlb_load_misses.walk_*` 等 page walk 周期事件在此 VM 上被 PMU 屏蔽
